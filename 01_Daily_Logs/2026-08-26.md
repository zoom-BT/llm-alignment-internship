## Concepts Covered Today (In English)
### Separating a Research Journal from a Codebase
- **Why code and journal don't have to live in the same repository:** the vault (notes, logs, proposals) documents *why* and *what was decided*; a separate code repository documents *how it runs* — mixing them makes both harder to navigate as the project grows past a single-week experiment.
- **Carrying over tested infrastructure deliberately, not wholesale:** copying only the generic, already-debugged pieces (quantization config, warmup-step conversion, checkpoint cleanup) into the new repository, while leaving Week 1-3's task-specific code (SFT dataset formatting, ORPO) behind — reuse without dragging along what doesn't apply.
- **A shared interchange format for two data conditions:** formatting both Native-DPO and Translated-DPO into the same ChatML structure so the trainer can't distinguish the two conditions except by content — necessary for a fair H1 comparison.

### Checking Whether a Hypothesis Is Already Answered, Before Testing It
- **A hypothesis can be true, testable, and still worthless.** H1 was all three: well-posed and measurable, but a systematic review (arXiv:2608.14626, PRISMA over ~1,500 papers) shows the field already settled it — naively translated safety data degrades alignment, and quality filtering mitigates it. Confirming a known result is not a contribution.
- **A systematic review is a map of what is *not* known.** Its "future work" section is a list of unclaimed ground. This one states that continued pre-training is not covered as a method, and calls for validating PEFT and cross-lingual transfer specifically in African languages — which is exactly H2. The gap was located by reading what a review omits, not by guessing.
- **Where the novelty sat was not where the title said.** The interesting variable was the *backbone* (CPT vs. standard), not the *data* (native vs. translated). Recentring on it also removed the dependency on a genuinely native dataset, which the previous days had established does not exist among the candidates.

### Verifying Data Assumptions in Code Rather Than by Inspection
- **A near-miss worth recording:** the pipeline first produced 14 pairs instead of the expected ~1,100. The cause was an off-by-one in an earlier manual analysis — PASS and FAIL diverge at the *first* assistant response, not the last. Running the pipeline surfaced in seconds what eyeballing the data had gotten wrong.
- **Silent truncation is the dangerous kind of bug.** `max_seq_length: 1024` would have cut 13.8% of examples. Nothing would have crashed; the run would have completed and reported a plausible loss curve, having trained on preference pairs whose responses were chopped off. Measuring token lengths against the real tokenizer *before* the run is cheap; discovering it afterwards costs a GPU session and produces results that cannot be trusted.
- **Contamination has to be tested at the right granularity.** Checking that no `row_id` sits on both sides of the split is not enough — what actually matters is that no *prompt* does. Both are checked, because two pairs carved from one `row_id` share a prompt word-for-word.
