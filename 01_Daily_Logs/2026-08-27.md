## Concepts Covered Today (In English)
### Implementing an Evaluation Metric Before Trusting It
- **"Evaluate without modification" as a deliberate first step:** running the unaligned models before any DPO training isolates what the backbone alone contributes, so later B2/B3/B4 deltas are measured against a real, not assumed, starting point.
- **A metric is only as good as its classifier:** RR%/Over-RR% depend on correctly detecting a refusal in the model's own words across four languages — worth manually checking a sample before trusting the aggregate percentage.
- **Reproducibility as a script, not a notebook cell run once:** writing the evaluation as a callable script (not one-off notebook code) is what makes "reproducible evaluation script" an actual deliverable rather than a one-time result.

### Reading the Benchmark's Own Evaluation Code Before Writing Your Own
- **The decisive lesson of the day.** A dataset card, and even a paper, describe what a benchmark *contains*. The evaluation script describes what it *measures*. Those are not the same, and here they diverged completely: UbuntuGuard's task is to judge a `(policy, transcript)` pair as PASS/FAIL, scored by accuracy and macro F1 — not to generate responses and measure refusals.
- **The tell was in the data, and it was visible earlier.** The PASS responses cite Ghana's Road Traffic Act and Kenya's NCIC; they engage the question helpfully. Nothing about them resembles a refusal. Inspecting examples before implementing a metric is what "manually inspect dataset examples and labels" is actually for.
- **A metric that measures nothing still produces numbers.** RR% implemented on this data would have run, returned percentages, and supported a whole results table — all meaningless. Failures that produce plausible output are the ones worth guarding against, the same lesson as yesterday's silent truncation at `max_seq_length: 1024`.
