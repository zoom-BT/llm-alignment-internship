## Concepts Covered Today (In English)
### Autoregressive Generation & Baseline Metrics
- **Autoregressive Decoding:** Generating text token by token where each new token is conditioned on all previously generated tokens.
- **Sampling Parameters:** - `temperature`: Controls randomness in output distributions.
  - `top_p` (Nucleus sampling): Limits token selection to a cumulative probability threshold.
- **Perplexity & Benchmark Metrics:** Quantifying model uncertainty and output quality prior to fine-tuning.

### Deep-Dive Recap: Sampling, Batching Bugs, and a Real Baseline Number

**Sampling parameters, seen on real logits, not just described:** for the prompt "The best way to learn machine learning is", the raw distribution gave `' to'` 67% probability. Dividing logits by `temperature=0.7` before softmax pushed it to 87% (amplifying the gap); dividing by `1.5` dropped it to 22% (flattening the gap, letting near-invisible candidates like `' the'` become real options). `top_k=5` hard-deletes everything outside the 5 best and renormalizes; `top_p=0.9` adapts the cutoff size instead of fixing it (needed 6 tokens here, not 5, to cross the 90% cumulative threshold) — the actual difference between the two, not just "two similar-sounding options."

**A real, silent bug found via batching:** naively batching multiple prompts with the tokenizer's default right-padding corrupted generation for the shorter prompt ("The capital of France is" → garbled "Human Brain..." prefix) while leaving the longer, unpadded prompt untouched — because a decoder-only model always predicts from the *last* position, and right-padding pushes that position past the real content. `transformers` itself warns about this; the fix is forcing `padding_side="left"`. This is exactly the kind of bug that would silently produce misleading evaluation numbers for a random subset of examples without ever raising an error.

**A second real bug, in `compute_perplexity`:** a one-token response ("yes") has no valid next-token target, so the model's loss for it is `NaN` — and `NaN * 0` is still `NaN` in floating point, silently poisoning the *entire* running sum, not just that one example. Fixed by skipping any text that tokenizes to fewer than 2 tokens.

**A third, purely local problem — not a code bug:** loading the model in FP32 (~1.9 GB, per Monday's benchmark) segfaulted with only ~1.9 GB of RAM free. Switching to BF16 (~950 MB) fixed it locally; separately, none of the generation/evaluation functions were moving the model or inputs to GPU at all, which would have silently run everything on CPU even on Kaggle's T4 — fixed by using `model.device` and `get_device()` throughout.

**The real baseline, finally:** run on Kaggle T4 (not locally — a full run was estimated at ~45 minutes on this laptop's CPU vs. seconds on GPU), on the complete 1,502-example test split: **perplexity = 13.92** for Qwen2.5-0.5B (base, not fine-tuned) on databricks-dolly-15k responses. This is the "before" number the contract's Week 1 deliverables ask for — the "after" comes once SFT training happens (Thursday/Friday).

**The evaluation process itself, step by step:** `compute_perplexity` loops over each test response, tokenizes it, and — critically — does a single **forward pass** through the model with `labels` set equal to `input_ids`. That's the key distinction from generation: no new tokens are produced, the model is just asked "how well did you predict each token here?", and Hugging Face returns that as a mean cross-entropy loss. Two details matter for correctness: (1) that per-text loss has to be multiplied back out by its token count before summing across texts, otherwise a one-sentence response and a five-paragraph one would count equally in the average — wrong, since perplexity is a per-token quantity; (2) texts under 2 tokens are skipped entirely, since there's no next-token target to score (the root cause of the NaN bug). `run_benchmark` is the thin layer around that: it turns `config.yaml` entries (`base_model_name`, `precision`, `dataset_name`) into an actually-loaded model/tokenizer/dataset, moves the model to whatever device `get_device()` finds, calls `compute_perplexity` inside a `torch.no_grad()` block (no gradients needed — nothing is being trained), and writes a self-describing JSON (model name, dataset, split, example count, and the number itself) rather than just the bare float, so the result file still makes sense on its own months from now.
